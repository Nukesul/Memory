# Memoris: вход по приглашению и защита данных (фаза 1)

## Цель

Только участники класса, вошедшие под своим аккаунтом, видят данные. Каждый меняет только своё. Личные сообщения видят только двое участников. Фото закрыты от посторонних. Всё это проверяет база, а не интерфейс.

## Как устроен вход

1. Админ (Нурсултан, `person_id = 2`) в админке нажимает «Пригласить» у одноклассника.
   - База создаёт случайный код (128 бит) и хранит только его SHA-256 хэш.
   - Код живёт 14 дней и срабатывает один раз.
   - Ссылка `…/#/join/<код>` показывается админу один раз, и он сам отправляет её.
2. Одноклассник открывает ссылку и видит «Приглашение для <имя>». Он вводит email и пароль (от 8 символов).
3. Edge Function `auth-invite` с сервисным ключом (он живёт только на сервере) делает следующее:
   - атомарно «гасит» код;
   - создаёт пользователя Supabase Auth с подтверждённым email;
   - записывает в защищённое `app_metadata` поле `person_id`, которое пользователь не может изменить сам.

   После этого браузер входит по email и паролю. Сессия хранится и обновляется сама, так что при повторном открытии вход сохраняется.
4. **Восстановление пароля.** Админ создаёт ссылку сброса `…/#/reset/<код>`, которая действует 24 часа и один раз. По ней пользователь задаёт новый пароль, и все его старые сессии завершаются.
   - Сброс через письмо на почту включается позже, когда в Supabase будет подключён свой SMTP. Стандартная почта Supabase отправляет письма только членам команды проекта.
5. **Чужие аккаунты бесполезны.** Если кто-то зарегистрируется в обход приглашений, у него не будет `person_id` и действующей записи в `accounts`, поэтому RLS не покажет ему ни одной строки.

## Новые таблицы

| Таблица | Поля | Кто видит |
|---|---|---|
| `admins` | `person_id` | никто, только функции |
| `accounts` | `person_id` PK, `user_id` (auth.users), `email`, `created_at`, `disabled` | сам участник; админ через RPC |
| `invites` | `id`, `person_id`, `kind` (`join`/`reset`), `code_hash`, `expires_at`, `used_at`, `created_at` | никто, только функции |

`presence` получает поле `visible`, чтобы участник мог скрыть свой онлайн-статус.

## Вспомогательные функции (`security definer`, `search_path` закреплён)

- `my_person()` возвращает `person_id` из JWT, но только если `accounts` подтверждает связку `auth.uid()` с этим `person_id` и аккаунт не отключён. Иначе возвращает `null`.
- `is_member()` — это `my_person() is not null`.
- `is_admin()` проверяет, что участник есть в `admins`.
- `claim_invite(hash, kind)` гасит код атомарно (`update … where used_at is null and expires_at > now()`). Её может вызывать только `service_role`.
- `admin_create_invite`, `admin_members`, `admin_revoke_invite` требуют `is_admin()`.
- Старые RPC с PIN заменяются версиями, которые проверяют `is_admin()`. Таблица `admin_secret` удаляется.
- `react_message(id, emoji)` ставит или снимает реакцию только на видимом сообщении.
- `capsule_meta()` возвращает список «кто уже написал» без текстов.

## Политики RLS (`anon` не получает ничего)

| Таблица | Чтение | Запись |
|---|---|---|
| profiles | участники | свою строку (админ — любую) |
| notes | участники | создать от себя; удалить автор, адресат или админ |
| votes, autographs, daily_answers | участники | только свои строки |
| messages | общий чат класса, или я отправитель или получатель | создать от себя; править только `text` и `edited_at` своих; удалить своё (админ — любое) |
| capsules | своё, а после даты открытия — всё | своё и только до открытия |
| presence | `visible` или своё | своё |
| announcements | участники | только через RPC админа |
| push_subs | никто | RPC только для своего `person_id` |
| storage `photos` | участники (бакет становится **приватным**) | загрузка и удаление только в своей папке `<person_id>/…`; админ может удалить любое |

Фото открываются по подписанным ссылкам на 7 дней, которые кэшируются в браузере. В базе адреса не меняются, поэтому откат возможен без правки данных.

`execute` на все функции отзывается у `public` и `anon`.

## Порядок миграций

1. **Резервная копия:** схема `backup_20261126` с копией всех таблиц и текстом всех текущих политик.
2. **Аддитивная часть** (сайт продолжает работать как раньше): `admins`, `accounts`, `invites`, функции, Edge Function. Её проверяю вызовами из базы через `pg_net`.
3. **Новый клиент** с экраном входа, приглашениями и подписанными ссылками на фото. Проверяю его в браузере.
4. **Переключение** одной транзакцией: строгие политики, приватный бакет, отзыв прав `anon`. Сразу после этого выкладывается новый сайт, и в базе проверяются роли «гость / участник / чужой участник / админ».

## Откат при ошибке

- База: `supabase/rollback/2026-11-26-strict-rls.sql` возвращает прежние политики и публичный бакет. Данные не удаляются, они лежат в `backup_20261126`.
- Сайт: повторная выкладка предыдущей сборки `gh-pages` (коммит `aa9cd5f`).
- Новые таблицы аддитивны и старому клиенту не мешают.

## Что останется после фазы 1
